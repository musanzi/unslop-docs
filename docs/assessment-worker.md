# Assessment worker reference

The API saves a validated original and commits its `queued` document row in one transaction, queued for the initial assessment only. It does not import or call the DeepSeek provider. Existing originals retain `stored` status after migration and are not sent to a provider retroactively.

The worker claims an initial assessment or a rewrite. Initial and final assessments call the private local detector service. DeepSeek only edits, using the pinned unslop skill. After editing, the worker constructs and validates the revised DOCX, saves it, reads its text again, and requests the final local check.

Results use rubric `local-detector-v1` and a required `detection` object. The object records the pinned Oculus model revision, aggregation method, model score, input hash, UTF-16 character count, token count, segment count, and check time. The provider rejects malformed results, unknown model revisions, and hashes or lengths that do not match the submitted text. Records outside this contract are not exposed as detector results. There is no automatic fallback to LLM scoring.

The detector divides all tokens into balanced windows of at most 510 content tokens and returns the token-weighted mean of their model outputs. The UI displays that value on a 0–100 scale. It is neither a calibrated document probability nor a percentage of AI authorship. Text below 50 whitespace-delimited words, above 150,000 UTF-16 code units, or above 128 windows receives an unavailable result. An unavailable result has no score and does not prevent editing. Transport failures use the existing bounded retry flow.

The detector runs on the app server without a paid API or credentials. It downloads pinned model files once and caches them in the `detector_models` volume. Document text stays in memory and is not sent to Hugging Face. DeepSeek still receives the passages selected for rewriting. See [the local detector setup and limitations](../services/detector/README.md).

## Settings

| Setting                     | Required | Default                | Meaning                                                             |
| --------------------------- | -------- | ---------------------- | ------------------------------------------------------------------- |
| `DEEPSEEK_API_KEY`          | Yes      | None                   | Worker-only provider credential                                     |
| `DEEPSEEK_MODEL`            | Yes      | None                   | Explicit available model identifier                                 |
| `ASSESSMENT_TIMEOUT_MS`     | No       | `300000`               | Initial assessment deadline from its claim                          |
| `PROCESSING_TIMEOUT_MS`     | No       | `900000`               | Rewrite deadline from its claim, including the final assessment     |
| `DEEPSEEK_TIMEOUT_MS`       | No       | `60000`                | Maximum editing-provider wait                                       |
| `LOCAL_DETECTOR_URL`        | No       | `http://detector:8090` | Private detector origin; Compose fixes this to its internal service |
| `LOCAL_DETECTOR_TIMEOUT_MS` | No       | `300000`               | Maximum wait for a local check                                      |
| `DETECTOR_THREADS`          | No       | `2`                    | Detector CPU threads, clamped to 1 through 16                       |

Choose a model that supports JSON output from [DeepSeek's model documentation](https://api-docs.deepseek.com/quick_start/pricing/). There is no implicit model fallback. All worker durations must be positive integer milliseconds at most `2147483647`. Time spent at the preview waiting for the user is outside both deadlines. The effective wait cannot exceed the persisted deadline. Startup reports missing settings by name without showing their values.

The worker disables LangChain verbose output and LangSmith tracing. The SDK logger is off, and provider exceptions become fixed failure messages. Neither provider responses nor document text are logged. Compose passes DeepSeek settings only to the worker. Tests inject fake providers or a fake HTTP transport. There is no runtime fake-provider flag or authentication bypass.

DeepSeek editing requests set `thinking: { type: 'disabled' }` so the 4,096-token response budget is available for JSON. DeepSeek enables thinking by default. A live check exhausted the budget on reasoning and returned no content. The [thinking-mode reference](https://api-docs.deepseek.com/guides/thinking_mode/) documents this setting.

## Lifecycle

Each document row carries a durable `phase`: `assessment` for the automatic initial assessment and `rewrite` for the user-requested rewrite with its final assessment. `queued` becomes `processing` on an atomic claim. An assessment claim needs no allowance reservation; a rewrite claim requires an active reservation. The claim sets the deadline for its phase, `processingStage` `assessing` or `editing`, and a 30-second lease renewed every 10 seconds and before each provider call. The processing deadline is persisted once and never extended by a heartbeat. A live worker performs recovery before each claim.

An assessment claim reads the original, requests `local-detection:initial:v1`, and publishes the validated assessment and preview in one update that sets `assessed`, clears the claim, stage, and deadline, and leaves no reservation. The document then waits for the user without a deadline. A failed assessment sets `failed` with the phase `assessment`, no assessment, and nothing to release.

A rewrite claim edits each chunk with the persisted strength, reports completed and total chunks in `editingCompleted` and `editingTotal`, constructs and validates the revision, writes it under a new private key, and saves the key, size, and notices on the processing row while advancing the stage to `final-assessment`. Only then does it request `local-detection:final:v1` on the revised text. Publication sets `completed`, stores the final assessment or null, clears the claim, stage, and progress, and charges the reservation in the same statement. Failure before the revision is saved sets `failed` with the phase `rewrite`, keeps the initial assessment, preview, and strength, releases the reservation, and removes the written file. Once the revision is saved, no failure discards it: an exhausted, malformed, cancelled, or interrupted final assessment publishes the revision with a null final assessment, and the API reports `finalScoreUnavailable`.

Recovery fails expired deadlines and lease-expired attempts that are not resumable, releasing their reservations, unless the row already holds a saved revision; those rows are published with an unavailable final score and charged. After lease expiry, recovery resumes attempts whose requests have only validated successes or scheduled temporary failures, including a final assessment awaiting its retry, which reads the saved revision instead of editing again. Graceful shutdown aborts an active request; during editing it fails the claim, and during the final assessment it publishes the saved revision without a score. A scheduled retry holds no active lease and survives shutdown.

Publication requires the same claim token, `processing` state, and the phase-specific guards. A late provider response cannot replace failure or recreate a deleted document. SQL updates return rows through a common database boundary that the tests exercise in embedded PostgreSQL. `tools/check-allowance-postgres.cjs` runs the last-slot race, duplicate Unslopify and retry requests, month-boundary charging, and deletion contending with publication against a disposable real PostgreSQL database; `bash tools/check-allowance-postgres.sh [api-container]` runs it inside the API container.

Each provider request has its own finite wait, bounded by the remaining deadline of its phase. Both LangChain and its underlying SDK have zero retries. LangGraph nodes have no library retry policy. The worker persists request checkpoints in PostgreSQL and replays the graph using validated cached results when resuming an attempt. Each editing request has a stable chunk ID and produces independently validated span results. The [revision reference](document-revisions.md) describes construction and publication. Only validated revised output charges usage. The [queue decision](adr/0003-keep-document-jobs-in-postgresql.md) and [ADR 0005](adr/0005-separate-assessment-from-user-requested-editing.md) record the transaction boundaries.

## Private reads and progress

`GET /documents` includes `status`, `phase`, `processingStage`, `progress`, `strength`, and a fixed failure explanation without assessment examples. `GET /documents/:id` adds the initial `assessment`, the `finalAssessment`, `finalScoreUnavailable`, and `revisionNotices`. Each assessment carries its `rubric` and, for local checks, a `detection` object. Results outside the detector contract return null. `GET /documents/:id/preview` returns the read-only preview published with the assessment: ordered blocks of kind `heading`, `paragraph`, `list-item`, `table`, or `protected`, with heading or list levels from 1, formatted inlines, table rows and cells, and protected element reasons. Another user, an admin, a malformed identifier, a missing document, and a document without a published preview receive the same 404 body. Signed-out callers receive 401. Responses use `Cache-Control: private, no-store`.

`POST /documents/:id/unslopify` accepts `{ "strength": 1..100 }`, defaulting to 50, for an owned `assessed` document. It locks the row, reserves one allowance slot, and queues the rewrite in the same transaction, persisting the strength with the attempt. A second click, a queued or processing rewrite, a completed document, and an unassessed document receive 409 without a second reservation; an exhausted allowance receives the same 409 explanation as before and leaves the preview available.

Progress is indeterminate during `assessing` and `final-assessment`, where `progress` is null. During `editing`, `progress` reports completed and total chunks, and construction and validation keep the final counts under `validating`. Reloading never restarts completed work because checkpoints survive claims. The original remains downloadable in all processing states. A `completed` document also exposes its validated revised download and a review reminder.

## Durable provider retries

Migration `1793880500000-ProviderRetries` adds a processing attempt identifier, private request checkpoints, and the next eligible request time to the existing document row. Initial claims assign the attempt identifier and deadline. Resumed claims rotate the claim token and retain the attempt identifier, start time, and deadline.

`local-detection:initial:v1` identifies the initial assessment, `edit:<chunk ID>` identifies each planned editing request, and `local-detection:final:v1` identifies the final assessment of the revised text. Each checkpoint contains the input hash, call count, state, and either validated output or fixed failure metadata. The input hash covers the instructions and request data. A changed request fails recovery without another provider call. Checkpoints contain document text only in validated outcomes, remain excluded from normal entity selection and API responses, and disappear with the document row.

Before a provider call, a guarded SQL update increments the call count and marks the request `running`. A validated response becomes `succeeded`. Temporary failures become `retry` after calls one and two, with delays of 1,000 and 2,000 milliseconds. PostgreSQL stores the next eligible time and expires the lease in the same update. The document remains `processing`, and the worker returns to its polling loop. Polling or other work can increase the effective delay. A resumed rewrite reuses successful chunk results without sending them again, and a resumed final assessment reads the saved revision instead of editing again.

Timeouts, connection failures, HTTP 408, HTTP 429, and HTTP 5xx are temporary. Authentication failures, other request rejections, malformed or incomplete responses, output-validation failures, cancellation, and unknown errors receive no automatic retry. Failure metadata contains only a fixed category and an optional numeric HTTP status. Provider messages, bodies, headers, request IDs, credentials, and exception causes are discarded.

Every request start and checkpoint update requires the current claim token, processing state, valid lease, and unexpired deadline. A response received after timeout cannot update a checkpoint. A hard stop before the response checkpoint commits leaves `running`; recovery fails this unknown outcome instead of blindly repeating it. A hard stop after a success or retry checkpoint commits can resume safely. These boundaries provide at-most-three calls per request, not exactly-once provider execution across a network failure.

The phase deadline also bounds backoff and cached-result reconstruction. Recovery never extends it. Automatic retries create neither a new job nor a new processing attempt. Unslopify reserves once before the first editing request, and the reservation survives resumed claims and final-assessment retries. Charging and release belong to terminal transitions. An authorized user retry resets the request checkpoints and creates a distinct processing attempt on the next claim.

Stop workers before rolling back the retry migration. Rollback fails active attempts that use checkpoints, then removes retry metadata. Originals, completed assessments, and revised files remain intact.

## User retries

`POST /documents/:id/retry` locks the owner-matched document row before checking that its status is `failed`, then branches on the failed phase. A failed initial assessment is queued again without any reservation. A failed rewrite acquires the owner lock through `MonthlyAllowance.reserve`, creates a new reservation, and is queued again with its initial assessment, preview, and strength intact. The reservation uses the time after the owner lock is acquired. A competing retry waits for the document lock and receives HTTP 409 after the first transaction queues it.

Queueing clears the previous failure, processing stage, claim token, lease, attempt identifier, start time, deadline, request checkpoints, and next request time. The original storage key, size, filename, and creation time stay unchanged. The next claim assigns a new attempt identifier and deadline. Each request gets its initial call and up to two automatic retries again. Old claim tokens cannot publish a result or release the new reservation.

The retry API makes no provider call. A rewrite retry returns HTTP 409 when the allowance is exhausted and leaves the failed document, its assessment, and its strength unchanged. Rollback removes the new reservation if queueing fails. A completed document whose final score is unavailable is not retried: its revision is published and charged, and no separate assessment action exists.

## Deletion

`DELETE /documents/:id` works in every state. It locks the owner-matched row, removes the original and any revised DOCX from private storage, and then deletes the row. The row carries the preview, both assessments, revision notices, and request checkpoints, so nothing of the document outlives it. Files go before the row: a removal failure returns HTTP 503 and leaves the record pointing at the remaining file, so the owner can repeat the deletion, and a file is never left without a record. Storage removal is idempotent, so a repeat after a lost database acknowledgement finishes the job. Another user and the admin receive the same HTTP 404 as a document that never existed, and so does a repeated delete once the document is gone; the web client treats that 404 as already deleted.

A completed document keeps its charged reservation, and an assessed preview or failed document has none to release. A queued or processing rewrite holds one active reservation, which the `release_document_reservation` trigger releases in the deletion transaction, so repeated deletes cannot release twice and the allowance refreshes at once. A queued or processing initial assessment holds no reservation, so deleting it changes no allowance and creates no credit.

Deleting an active document ends its attempt without a terminal transition. Every worker update is guarded by the row, so after the deletion commits the lease renewal, request checkpoints, stage and progress updates, assessment publication, revision saving, and completion all update zero rows. The worker treats that as a lost claim: it sends no further provider request for the document, including the remaining chunks of a rewrite and the automatic retries of a request that already failed temporarily, because a retry needs a claim and a claim needs a row. A request already in flight is aborted at the next heartbeat or on return; DeepSeek may still process the text it received, and the worker discards the answer. Recovery after a worker restart finds no row to resume or fail.

Deletion and publication contend for the row lock, and exactly one of two states results. If the deletion commits first, no record, file, or active reservation remains and nothing is charged; a late completion updates zero rows, and the worker removes the revised file it wrote once the record no longer owns that key. If publication commits first, the deletion sees the completed row, removes the original and the revised file, keeps the charge, and deletes the row. A rewrite deleted during its final assessment already has a saved revision on the row; the deletion reads that key and removes the file. Unslopify and retry lock the same row, so after a deletion they receive HTTP 404 and reserve nothing, and a deletion after them releases the one reservation they created. `tools/check-allowance-postgres.cjs` exercises both lock orderings against real PostgreSQL; the unit specs script each ordering deterministically through a fake provider whose calls delete the document before returning.

## Migration

Migration `1793880900000-AssessThenUnslopify` adds `phase`, `strength`, `finalAssessment`, `preview`, `editingCompleted`, and `editingTotal`, and rewrites the check constraints so a failed or queued rewrite keeps its assessment and a processing rewrite may hold a saved revision. Completed documents receive the `rewrite` phase and stay downloadable; their assessments keep the old shape and report a null score. Legacy `assessed` documents keep their status and can be rewritten, with a null score and no preview. Documents that were queued or processing under the old automatic flow are queued again for the initial assessment, their attempt state is reset, and their old reservations are released so nothing is stranded or charged. Stop workers before migrating in either direction. Rollback fails active attempts as interrupted, releases their reservations, clears assessments from failed rows, and drops the new columns.
