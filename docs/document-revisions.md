# Revised document reference

An accepted upload runs only AI detection. Editing, construction, and validation start when the owner clicks **Unslopify**, and run through LangGraph with the persisted rewrite strength. An unavailable rate does not prevent editing. The existing LangChain `ChatDeepSeek` adapter sends every editing request. Both library retry settings remain zero. The worker persists automatic retries per request; the [worker reference](assessment-worker.md) describes reservations and charges.

## Editing and reconstruction

`planDocxEdits` uses the immutable reader model, read from the normalized main part described in the [DOCX support reference](document-support.md). Consecutive text nodes in one paragraph form one passage when their runs share bold, italic, hyperlink, and identical run properties, and only run tags, proofing marks, bookmarks, or rendered page breaks separate them. Word splits such runs by editing session, so this gives the provider whole sentences instead of fragments. A passage is not merged across tabs, line breaks, protected elements, or a formatting change, and it ends before trailing whitespace that the first text node could not preserve. Passages are split into spans of at most 1,600 characters, preferring spaces. Requests contain at most 3,200 text characters and 24 spans. Each span identifies the XML position of its first text node and its offset in the passage. Each chunk has a SHA-256 identifier derived from the normalized main part, the `docx-edit-v2` protocol version, and ordered spans. Identical input produces identical boundaries and IDs.

The provider returns one text replacement for every span, in order. Missing, duplicated, reordered, or malformed responses fail the attempt. Empty editable content requires no editing request. Protected content is never offered as an editable span. Fragmentary or uncertain prose can remain unchanged.

A single span whose replacement is empty, oversized, or contains control characters keeps its original text with a `response` notice. A replacement that only changes leading or trailing whitespace is accepted with the original whitespace restored. A replacement that fails a citation, quotation, number, reference, or language check keeps the original span text with a notice naming the check. The rest of the document is still edited. Nothing is replaced with incomplete provider output, and no material is dropped silently.

The graph collects validated results by chunk ID. `constructRevisedDocx` requires every chunk before constructing an archive. The worker persists validated request outcomes by processing attempt, operation, and chunk ID. Resumed attempts reuse successful chunks and revalidate them before construction. Failed or incomplete provider output is never cached as a success. The [worker reference](assessment-worker.md#durable-provider-retries) describes recovery and the shared deadline.

The pinned skill is subordinate to preservation instructions. The prompt states the rewrite strength from 1 to 100: up to 33 requests light edits that leave most spans untouched, up to 66 edits the sentences that show patterns, and higher values permit sentence-level rewriting; every level preserves facts and meaning. The prompt forbids translation, invented sources, deleted factual claims, and moving prose between spans. Source text is JSON-encoded in a separate user message and treated as untrusted data. Prompt separation constrains the request; it does not prove model obedience.

Construction replaces only text-node contents in the normalized main XML part. A merged passage is written into its first text node and the other text nodes of the passage are emptied, so every run and its properties survive. XML escaping prevents model text from becoming markup. Original run properties, list numbering, table markup, relationships, and protected inline XML survive. Other package parts are copied byte-for-byte. The original storage key is never written. The finished archive passes the existing reader and preservation checks before storage.

Construction also returns revision notices: `keptPassages` lists each span kept because of a failed check, with the check code, the span identifier, and an excerpt of at most 120 characters of the original passage; `uneditedElements` counts the protected elements by reason, such as `image`, `equation`, `reference-field`, `footnote`, `endnote`, `comment`, or `text-box`.

## Validation

Validation compares ordered blocks, heading levels, paragraph styles, list numbering and nesting, table dimensions, run formatting, hyperlinks, and text-node counts. It also compares the main XML outside editable text with the normalized original. Images, equations, reference fields, footnotes, endnotes, comments, headers, footers, and other package parts retain their original bytes. Because construction only rewrites text-node contents, these structural checks pass for the worker's own output; they guard against a damaged archive or a reader regression, not against formatting differences the user would accept.

Text checks compare recognized citations, quotations, numbers, month names, URLs, and reference markers at span, paragraph, and document level. At span level a failure keeps the original passage with a notice. At paragraph and document level a failure still fails the attempt, which can happen when recognized content spans two spans. Language checks reuse the reader's English/French classification. Changed short or uncertain text must retain at least half its distinct source words; a span that fails this is kept with a `language` notice. Returning unchanged text remains valid.

These checks do not establish semantic equivalence, factual accuracy, or exhaustive recognition of every citation convention. They cannot reliably distinguish all language changes in short or mixed passages. The model must preserve all claims and references, including those outside the recognizers. The UI asks owners to review the revised document before submitting it. Real provider evaluation remains necessary alongside deterministic tests.

A `RevisionValidationError` has one fixed check code: `response`, `structure`, `formatting`, `protected`, `citation`, `quotation`, `reference`, `fact`, or `language`. The entry displays the corresponding fixed explanation and a suggested action. Logs contain the check code, never document text or model output. Validation failures use the same terminal transition as provider failures and have no automatic retry.

## Publication and storage

The document row holds the revised key, revised byte size, processing stage, and nullable `revisionNotices` JSON. A processing rewrite can hold the saved revision and its notices. `GET /documents/:id` returns `revisionNotices` for completed documents. `processingStage` is `editing` or `validating` while a rewrite claim is active. The worker saves the revised key, size, and notices on the processing row; publication then changes the status to `completed`, clears the claim and stage, and charges the reservation.

The rewrite deadline covers editing, construction, validation, and saving the revision. The worker renews its lease before each request and every ten seconds. Saving the revision checks the claim token, status, lease, and deadline in the same SQL update. Failure, expiry, deletion, or a replaced claim before that point prevents publication, and a late provider callback cannot continue into storage. After the revision is saved, deadline expiry or lease loss publishes it instead of discarding it.

Only a complete, validated archive is written under a new random key with private file permissions. If saving the revision is rejected, the worker removes that file. If the database acknowledgement is lost, it checks whether the completed row owns that key before cleanup. An unavailable database or hard process stop can leave an inaccessible private orphan; the worker never risks deleting a revision whose publication is uncertain. No partial model output is exposed as a result. A future storage reconciliation task can remove confirmed orphans.

Both development and production workers mount the private documents volume for writing. The production worker uses the same `node` identity as the API. Neither mount is served publicly.

`GET /documents/:id/original` remains available to the owner in every state. `GET /documents/:id/revised` requires the owner and a completed document with revised metadata. Both endpoints return DOCX attachments and `Cache-Control: private, no-store`. Signed-out requests receive 401. Other users, admins, unknown IDs, malformed IDs, and unavailable revisions receive the same 404 response. Storage keys never appear in the API response.
